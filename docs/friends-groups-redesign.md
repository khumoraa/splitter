# Друзья и группы: аудит и дизайн-спецификация

Ветка `feature/friends-groups` (от `feature/scan-receipt`). Expo Go SDK 57.

## 1. Что есть / что сломано / чего нет (до переработки)

| Область | Состояние |
|---|---|
| Поиск `GET /friends/search?q=` | Только точное совпадение `uniqueId` (формат `#1234`, регистр/пробелы не нормализуются). По username искать нельзя. Нет лимита, rate‑limit, пагинации, статуса отношений. Отдаёт **email** найденного пользователя |
| Утечка email | `/friends` и `/friends/requests` отдают **email друзей и отправителей запросов** (`userPublicSelect` содержит `email`). Группы email не отдают |
| `username` в схеме | **Не уникален** и без индекса (уникальны только `email` и `uniqueId`). Различать людей можно только по `uniqueId` |
| `uniqueId` | `"#" + 4 цифры` (1000–9999 → 9000 значений), 5 попыток при регистрации. Вероятность отказа регистрации ≈ (n/9000)^5: 3 % при 4 500 пользователях, 55 % при 8 000. Формат зашит в QR/историю, поэтому не менял — см. решения |
| `POST /friends/request` | Нет проверки/ответа для статуса `REJECTED`/`BLOCKED`: повтор после отказа → 500 (нарушение уникальности) или дублирует связь в обратную сторону; нет кулдауна, нет rate‑limit; ответы без кодов |
| Отмена исходящего запроса | Отдельного эндпоинта нет; `DELETE /friends/:uniqueId` удаляет любую связь, включая `REJECTED`, — это позволяет обойти отказ и спамить |
| `POST /friends/join` (по ссылке) | Токен JWT 1–60 мин, **многоразовый**; принудительно ставит `ACCEPTED` даже поверх `REJECTED`/`BLOCKED` |
| `POST /groups/join` | Токен многоразовый (до 60 мин), живёт пока не сменился владелец; **автоматически создаёт дружбу с владельцем** (тоже поверх `REJECTED`/`BLOCKED`). Ошибки без кодов |
| `POST /groups/:id/members` | Владелец добавляет **любого** пользователя по `uniqueId` без его согласия и без проверки дружбы |
| Группы | Нет валидации названия (длина), лимита участников, rate‑limit; `leave` есть, на клиенте не используется; `promote` на деле **передаёт владение** (прежний владелец остаётся участником) — работает, но название вводит в заблуждение и на клиенте нет явного действия; удаление группы оставляет счета (`Session.groupId` → NULL), это нигде не объяснено |
| Приглашения пользователю в группу | **Нет**: пригласить можно только из друзей (и сразу, без согласия) или ссылкой |
| Коды ошибок | Только англоязычный текст `error`; клиент не может перевести |
| Фронтенд | Сторы на `any`, «loose»‑схемы zod, нет статуса отношений, нет отмены исходящих, нет «Покинуть группу» и «Передать владение», поиск без debounce/отмены запросов, нет поиска по списку друзей/групп, нет QR‑сканирования из раздела друзей (есть отдельный экран `scan-invite`) |

## 2. Принятые решения

- **Поиск** `GET /friends/search?q=&limit=&offset=&groupId=`. Нормализация: `trim`, регистр, ведущие `@`/`#`. Запрос вида `#1234` / `1234` / `name#1234` ищет по ID точно; иначе по username (точное → начало → вхождение, регистр не важен, сортировка стабильная: ранг, `lower(username)`, `id`). Минимум 2 символа (для ID — 4 цифры), `limit` ≤ 20, `offset+limit` ≤ 100, rate‑limit 30/мин на пользователя и 60/мин на IP. Ответ `{results:[{id, username, uniqueId, avatarUrl, relation, groupStatus?}], nextOffset}`; **email не отдаётся нигде**. `relation`: `none | friend | request_sent | request_received`; себя в результатах нет; удалённые аккаунты исключены. Если `username` совпадает у нескольких людей — отличаются `uniqueId`.
- **Индекс** по `lower(username)` не создаю: при текущем масштабе полный просмотр дешёвее поддержки функционального индекса (Prisma не описывает его в схеме). Если пользователей станет > ~50 тыс., добавить `CREATE INDEX … (lower(username) text_pattern_ops)` — запрос для него уже подходит.
- **Друзья**: отказ (`REJECTED`) хранится, повторный запрос от того же человека возможен через 7 дней (`REQUEST_COOLDOWN`), до тех пор для него запрос выглядит как «отправлен». Отмена — только для `PENDING` и только отправителем (`DELETE /friends/requests/:uniqueId`); `DELETE /friends/:uniqueId` удаляет только `ACCEPTED`. Лимит 20 новых запросов в час на пользователя.
- **Приглашения по ссылке** остаются JWT (не менял модель), но теперь `friends/join` и `groups/join` **не перетирают** `REJECTED/BLOCKED`, ошибки — с кодами `TOKEN_EXPIRED`, `TOKEN_INVALID`, `ALREADY_MEMBER`. Поведение «вступление по ссылке создаёт дружбу с владельцем» сохранено (не менял без нужды), но не поверх `BLOCKED`.
- **Приглашения в группу пользователю** (`GroupInvitation`): приглашает **только владелец** (как и ссылка‑приглашение и добавление; участники могли бы спамить чужими приглашениями); по умолчанию человек должен принять; принятие создаёт членство в транзакции и **не** создаёт дружбу. Лимиты: 30 приглашений в сутки на пригласившего, 20 ожидающих на группу, 50 участников в группе.
- **Прямое добавление** `POST /groups/:id/members` теперь только для **друзей** (`FRIENDSHIP_REQUIRED`); остальных — через приглашение.
- **Передача владения**: добавлен явный эндпоинт `POST /groups/:id/transfer {uniqueId}`; старый `…/promote` оставлен как синоним. Прежний владелец остаётся участником.
- **Удаление группы**: сами чеки и история **сохраняются** (связь с группой обнуляется), приглашения удаляются.
- Коды ошибок единые (`{error, code, …}`), клиент переводит по `code`.

## 3. Экраны

```
Друзья (/tabs/friends)            сегменты:  Друзья | Запросы (бейдж) | Найти
 ├─ Друзья:  поиск по списку, секции A–Я, свайп «Удалить» с подтверждением, pull‑to‑refresh
 ├─ Запросы: входящие (Принять/Отклонить, оптимистично с откатом), исходящие (Отменить)
 └─ Найти:   одно поле «Username или ID» (debounce 400 мс, отмена запроса), вставка из буфера, QR,
             карточки с кнопкой по статусу, «Показать ещё»; блок «Мой QR / ссылка» (копировать, Share)
Группы (/tabs/groups)             сегменты:  Группы | Приглашения (бейдж)
 ├─ Группы:  поиск, карточки (аватар‑коллаж/инициалы, число участников), создание (название + выбор друзей)
 └─ Приглашения: входящие (название группы и кто пригласил; Принять/Отклонить)
Группа (/tabs/groups/[groupId])   участники и роли, «Пригласить» (поиск по username/ID, мультивыбор),
                                  «Ссылка/QR», «Ожидают ответа» (владелец, отмена), переименовать, убрать участника,
                                  «Покинуть», «Передать владение», «Удалить группу» (двойное подтверждение с вводом названия)
```
Состояния каждого экрана: загрузка (скелетон), пусто, ошибка с «Повторить», офлайн (общий баннер; действия, требующие сети, отключены с пояснением). Права: недоступные роли действия скрыты или отключены с объяснением; сервер проверяет всегда.

Токены, темы, компоненты (`kit.tsx`: Screen, Section, Row, Button, Field, Banner, Skeleton, Card), хаптики, Reduce Motion, WCAG AA, цели ≥ 44 pt — как в `docs/profile-redesign.md`. Аватары: `ProfileAvatar` (expo‑image, инициалы на цветном фоне).

## 4. Коды ошибок

`UNAUTHORIZED, FORBIDDEN, NOT_FOUND, VALIDATION, RATE_LIMITED, CANNOT_ADD_SELF, ALREADY_FRIENDS, REQUEST_EXISTS, REQUEST_RECEIVED, REQUEST_COOLDOWN, REQUEST_NOT_ALLOWED, ALREADY_MEMBER, NOT_A_MEMBER, CANNOT_INVITE_SELF, INVITATION_EXISTS, INVITATION_NOT_PENDING, FRIENDSHIP_REQUIRED, OWNER_CANNOT_LEAVE, CANNOT_REMOVE_OWNER, GROUP_FULL, INVITE_LIMIT, TOKEN_EXPIRED, TOKEN_INVALID`.
