# Учёт оплат, финансы и iOS‑доработка: аудит и спецификация

Ветка `feature/payments-ios` (от `main` = все предыдущие ветки + проход по качеству). Expo Go SDK 57.

## 1. Что есть / чего нет

| Область | Состояние до работы |
|---|---|
| Финализация `POST /sessions/finalize` | Считает доли в целых сотых (`toMinor` ×100 **для любой валюты**, у UZS/JPY получаются «копейки» 20 293,33) и пишет **только JSON** в `SessionHistoryEntry.payload`; таблицы `SessionParticipant` / `ReceiptItem` / `ItemAssignment` не заполняются. Участник = `uniqueId` из тела запроса (существование пользователя не проверяется) |
| Плательщик | Всегда создатель сессии (`payer` вычисляется, не хранится). Выбора «кто платил» нет |
| Редактирование после финализации | Создатель может вызвать finalize снова — история **перезаписывается** целиком |
| Учёт оплат | **Нет**: ни долгов как записей, ни платежей, ни статусов, ни журнала |
| «Кто кому должен» | Только на клиенте (`computeSettlements`): все должны плательщику; отрицательная доля (скидка больше заказанного) разворачивает долг |
| История | Список и карточка счёта; статуса оплаты нет, фильтров нет |
| Финансовый раздел | Нет (ни сводки «мне должны / я должен», ни по людям, ни по группам) |
| Выписка / экспорт | Нет. `expo-print` и `expo-sharing` есть в Expo Go SDK 57 |
| Свайп назад от края | **Не работает почти нигде**: весь раздел `app/tabs/*` — это навигатор `Tabs` со скрытой панелью; у вкладок нет жеста «назад» по определению. Корневой `Stack` содержит только вход/регистрацию |
| Заголовки | Собственный общий заголовок (`GlobalTabsHeader`): «‹ Назад» только у экранов профиля, «‹ Главное меню» у друзей/групп/счетов (это `replace`, не возврат) |
| Стекло | `expo-glass-effect` (~57.0.4) и `expo-blur` (~57.0.3) есть в `bundledNativeModules.json` SDK 57; в проекте не используются. `expo-router` 57 содержит `native-tabs` |

## 2. Решения

**Модель данных** (миграция — план в чате до применения):
- `Obligation` — долг одного человека другому по одному счёту: `amountMinor` (целые минимальные единицы валюты), `currency`, `status` (`UNPAID`, `PARTIALLY_PAID`, `PAID_PENDING_CONFIRMATION`, `PAID`, `FORGIVEN`, `CANCELLED`), денормализованные `confirmedMinor` / `pendingMinor`. Один активный долг на пару (счёт, должник) — частичный уникальный индекс.
- `ObligationPayment` — отметка оплаты: сумма, способ (`CASH`, `TRANSFER`, `OTHER`), заметка, кто записал, статус (`PENDING` — «я оплатил» от должника; `CONFIRMED` — подтверждено или записано получателем; `REJECTED` — с причиной), `Idempotency-Key` (уникален).
- `ObligationEvent` — журнал **только на добавление** (триггер БД запрещает `UPDATE`): кто, что, когда, сумма, заметка.
- Статус долга выводится из платежей в той же транзакции: подтверждено ≥ суммы → `PAID`; есть ожидающие → `PAID_PENDING_CONFIRMATION`; подтверждено > 0 → `PARTIALLY_PAID`; иначе `UNPAID`. `FORGIVEN` / `CANCELLED` — конечные.
- Сумма подтверждённых + ожидающих платежей никогда не превышает долг (`OVERPAYMENT`). Строка долга блокируется (`SELECT … FOR UPDATE`) на время записи.
- Финализация переводится на **настоящие минимальные единицы валюты** (UZS/JPY — целые) и синхронизирует долги: совпадающие остаются, изменённые без платежей отменяются (`CANCELLED`, с событием) и создаются заново, изменение счёта с уже записанными платежами — `409 SESSION_LOCKED`.
- Права: участник счёта видит его долги; должник отмечает «Я оплатил»; получатель подтверждает, отклоняет (с причиной), записывает «Получено», прощает, напоминает (не чаще раза в 24 ч на долг). Создатель, не являющийся получателем, чужие статусы не меняет. Всё проверяется на сервере.
- Удаление аккаунта: долги, платежи и события переходят на служебного «Удалённый пользователь» (как история), счета‑одиночки удаляются каскадом.
- Старые счета получают долги `UNPAID` обратимой миграцией данных (из JSON истории).

**Навигация:** `app/tabs/_layout.tsx` становится `Stack` (тот же общий заголовок, кнопка «Назад» по `back`), что даёт системный свайп от края и стандартные переходы на всех экранах; `fullScreenGestureEnabled` — на обычных экранах; на камере/обработке скана и формах с несохранёнными данными — перехват (`usePreventRemove`) с подтверждением; формы оплаты — `presentation: 'formSheet'`. `NativeTabs` не вводим: в приложении нет видимой панели вкладок, переход потребовал бы перестройки навигации на стеки по вкладкам — риск без пользы для этой задачи.

**Стекло:** `GlassSurface` — `GlassView` из `expo-glass-effect`, если `isLiquidGlassAvailable()`; иначе `BlurView` (`systemChromeMaterial`); при «Понижении прозрачности» и на Android — сплошной фон. Только на 3–4 элементах: нижняя панель действий экрана итогов, сводная карточка «Финансы», плавающие кнопки, заголовок выписки. Текст на стекле — цвета `text` темы (контраст проверяется тестом на фоне‑подложке).

## 3. Экраны

```
Итоги счёта (finish) / Карточка истории
  ├─ «Расчёт»: итог, налог/чаевые/скидка, доли, плательщик
  ├─ по каждому должнику: строка статуса (иконка + текст) и действие по роли
  │     должник: «Я оплатил» (способ, комментарий, частичная сумма) → лист formSheet
  │     получатель: «Получено», «Подтвердить», «Отклонить», «Простить», «Напомнить»
  ├─ «Журнал» (кто, что, когда)
  └─ «Поделиться расчётом» (Share), «Выписка PDF» (expo-print + Share)
Финансы (вход с главной и из профиля)
  ├─ сводка по валютам: «Вам должны» / «Вы должны» (никогда не суммируются разные валюты)
  ├─ фильтры: статус, период, группа; поиск по человеку
  ├─ люди с балансами → человек: все счета, платежи, баланс, «Напомнить», выписка
  └─ группы с прогрессом погашения
История: метка «Оплачено / Частично / Не оплачено» и фильтр по статусу
```
Статусы никогда не передаются только цветом: иконка + текст. Деньги — целые минимальные единицы, `Intl` по валюте и языку, нулевые/отрицательные значения, длинные суммы переносятся.

## 4. Юридическая граница
Приложение не проводит платежи и не хранит деньги; только записи о долгах и отметки о расчёте вне приложения. Выписка — нейтральный документ без логотипов банков, печатей и «официальных» номеров; короткий ID = номер счёта в приложении. Внизу каждой выписки и экспорта: «Settlement generated by Splitter for personal record-keeping. Not a payment or tax document.» (en/ja/uz). В выписках только имя пользователя и аватар, без email и телефонов.

## 5. Итог реализации

Сделано по спецификации, с уточнениями: «кто платил» не выбирается — плательщик по‑прежнему создатель счёта (селектор не нужен, пока это правило не меняется — решение за владельцем продукта); фильтр статуса в истории работает по загруженным последним 50 счетам (сервер поддерживает и `paymentStatus` в запросе); стекло использовано на трёх элементах: панель действий расчёта, карточки сводки «Финансы», шапка баланса с человеком. Подробная таблица и проверки — `INTEGRATION_REPORT.md`, раздел 16.
